Erro na estimação dos hiperparâmetros do bsvarSIGNs 3.0

Para: Jota De: Dudu Data: 14/10/2026 Pacote: bsvarSIGNs 3.0 (CRAN)

Resumo

  • Ao estimar a prior hierárquica (Giannone, Lenza e Primiceri, 2015) com spec$estimate_hyper(), a cadeia dos hiperparâmetros fica presa numa região inválida. Todos os valores de μ, δ, λ e ψ dessa estimação são inválidos, não só o do brent, onde o problema apareceu.
  • Causa: um erro no tratamento de falhas numéricas no código C++ do pacote. Um código de erro (−1e10) entra subtraído na conta e vira +1e10, a melhor nota possível.
  • Não é problema dos dados. O valor inicial que o pacote calcula para o brent está correto.
  • Decisão provisória: seguir a etapa 2 com os hiperparâmetros fixos na moda, calculada com uma função corrigida, e discutir com você a volta para a versão hierárquica (solução 2).

1. O sintoma

Modelo: 10 variáveis (4 externas via foreign: ust2y, ip_mundial, brent, vix; 6 domésticas: atividade, cpi_core, juro_curto, inclinacao, usdjpy, topix), p = 12, amostra de jan/2000 a jul/2026 (319 meses), prior hierárquica com λ, μ, δ e ψ estimados. Comando: spec$estimate_hyper(S = 15000, burn_in = 5000), com set.seed(123).

  • O ψ do brent saiu em 2.55e-06, mas a variância do erro de uma AR(12) do brent é cerca de 94.
  • Os traços de μ, δ e λ andavam em faixas minúsculas (por exemplo, λ entre 0.21831 e 0.21836), em ondas lentas. A cadeia estava praticamente parada.

2. A causa, em linguagem simples

  1. Para estimar λ, μ, δ e ψ, o pacote testa vários valores e dá uma nota a cada um, que é a log-posterior dos hiperparâmetros. Valores melhores ganham nota maior.
  2. A nota é uma subtração: nota = A − B. A é a verossimilhança marginal com dados + observações fictícias da prior; B é a mesma conta só com as observações fictícias.
  3. Quando algum hiperparâmetro fica muito perto de zero, a conta de B fica numericamente impossível (matriz quase singular). Nesse caso, o pacote escreve −1e10 no lugar, como aviso de erro.
  4. Como B entra subtraído, a nota vira A − (−1e10) = +1e10. Uma nota normal fica em torno de −4000.
  5. O algoritmo (Metropolis) interpreta +1e10 como o melhor ponto possível, vai para ele e nunca mais sai, porque qualquer ponto válido tem nota muito menor.

3. A causa, no código

Arquivo src/sample_hyper.cpp do pacote (versão 3.0, igual à do CRAN):

// log_ml(): verossimilhança marginal
// se alguma matriz não é positiva definida, devolve o código de erro
if (!Omega.is_sympd() or !Psi.is_sympd() or !XX.is_sympd()) {
  return -1e10;                                          // linha 131
}

// log_ml_dummy(): nota = A − B
double log_ml_plus = log_ml(..., Yplus, Xplus);          // A: dados + dummies
double log_ml_star = log_ml(..., Ystar, Xstar);          // B: só dummies
return log_ml_plus - log_ml_star + jacobian;             // linha 217: −(−1e10) = +1e10

A parte B usa só 11 observações fictícias (10 de soma de coeficientes e 1 de raiz unitária) para 121 coeficientes por equação. Ela depende quase toda da variância da prior de Minnesota, que é proporcional a λ²/ψ. Quando μ, δ ou algum ψ fica muito pequeno, a matriz de B fica quase singular e a conta falha.

Segunda forma do mesmo erro: quando A e B falham juntas, a nota vira −1e10 − (−1e10) = 0, ainda muito acima de qualquer valor válido (≈ −4000). Foi o que aconteceu quando deixei o otimizador rodar até o fim: λ foi para o limite (1e-06).

Por que a cadeia chega lá tão rápido: o pacote acha o ponto de partida com optim, mas para em 100 iterações sem convergir (código de convergência 1). A variância de proposta, montada a partir da Hessiana nesse ponto, fica larga demais, e a cadeia propõe valores perto de zero logo no início. No meu teste, ela caiu na região inválida na 9ª iteração.

4.2 Outros testes

  • Reprodução exata: com os mesmos dados e set.seed(123), a cadeia termina nos mesmos valores obtidos antes (μ = 0.0422, λ = 0.2192, ψ do brent = 2.555e-06). 100% dos draws mantidos estão na região inválida (nota > 0).
  • ψ fixos (hyper_psi = FALSE): a cadeia cai na armadilha por δ muito pequeno. Também 100% dos draws na região inválida.
  • Dados divididos por 100 (escala log, para a qual as hiperpriors padrão foram pensadas): o mesmo, 100% dos draws na região inválida.
  • Issues do GitHub: nenhum issue aberto ou fechado relata esse erro.

5. Consequências

  • Nenhum resultado de estimate_hyper() com esse modelo deve ser usado, nem nada estimado a partir dele.
  • Na segunda forma do erro (λ = 1e-06), o estimate() nem chega a rodar: falha com NA em vetor de probabilidades.
  • Ponto separado: estimate() leva cerca de 0.65 s por draw nesse modelo, ou seja, cerca de 1h50 para 10 000 draws. Isso vem do tamanho do modelo (10 variáveis × 12 defasagens, com o passo de importância do bloco externo), não do erro.

6. Soluções possíveis

Solução 1: fixar os hiperparâmetros na moda Decisão provisória

Encontrar o ponto de nota máxima com uma função corrigida (mesmas fórmulas do pacote, mas falha numérica = região proibida) e usar esse ponto para todos os draws do estimate(). O otimizador converge e a Hessiana é positiva definida.

moda <- c(0.0332882, 0.0792638, 0.428852,
          0.404967, 7.48788, 980.904, 2415.06,
          34.4905, 1.17210, 0.0205434, 0.0601272, 76.5726, 195.793)

# + 4 parâmetros de COVID, inativos
spec$prior$hyper <- matrix(c(moda, 1, 1, 1, 0.8), ncol = 1)
post <- estimate(spec, S = 2000)
A favorSimples e rápido. O estimate() roda sem NA. A literatura também usa essa alternativa (maximizar a verossimilhança marginal, o "empirical Bayes" discutido em GLP 2015).
ContraIgnora a incerteza sobre os hiperparâmetros, então não é a prior hierárquica do plano. Os valores valem para os dados até jul/2026 e precisam ser recalculados quando a base mudar.

Solução 2: amostrador corrigido O que o plano pede

Refazer o "passeio" do estimate_hyper() em R: um Metropolis em log(hiperparâmetros), com a nota corrigida e proposta baseada na Hessiana da moda válida. Os draws vão para spec$prior$hyper, e o resto (estimate(), projeção, identificação) continua no pacote.

Solução 3: conferir com o pacote BVAR

O pacote BVAR (Kuschnig e Vashold, 2021) usa a mesma prior de GLP, com limites para os hiperparâmetros. Serve para comparar os valores de λ, μ, δ e ψ.

A favorChecagem independente das soluções 1 e 2.
ContraNão tem bloco externo (foreign), exógenas nem ajuste de COVID. Serve como conferência, não como modelo final.

Solução 4: avisar os autores do pacote

Abrir um issue no GitHub (bsvars/bsvarSIGNs) com este diagnóstico. A correção no pacote seria tratar a falha de B como região proibida, em vez de subtrair o código de erro. Vale fazer de qualquer forma, mas não resolve o problema agora. Recompilar o pacote com a correção local também é possível, mas exige Rtools e manutenção da versão modificada.

7. Pontos para discutir

  1. Solução 1 ou 2 para a versão final? A proposta é seguir com a 1 agora e migrar para a 2 depois de revisar o código.
  2. Escala dos ψ na moda: os ψ ficam de 7 a 20 vezes acima das variâncias da AR, com λ = 0.43 (contra 0.2 no padrão). Na prior de Minnesota, λ e ψ se compensam, mas vale entender essa combinação.
  3. Hiperprior do ψ: o padrão do pacote é uma inversa-gama com moda 0.02², pensada para dados em log. Os nossos estão em log × 100.
  4. Projeção: o issue #91 do GitHub (aberto em 17/09/2026, sem resposta dos autores) relata que o forecast() não atualiza as defasagens 2 a p, começa um período antes e faz a projeção condicional período a período. Com p = 12, isso afetaria a etapa 2. Ainda não testamos; precisa ser verificado antes da avaliação fora da amostra.
  5. Bloco externo: ainda falta confirmar que o foreign impõe Axz = 0, como pede a seção 3.3 do plano.
  6. Ajuste de COVID: ainda não está no modelo (hyper_covid = NULL).

Reprodutibilidade: os scripts dos testes (reconstrução dos dados a partir do script de extração, sem alterá-lo; busca da moda; perfil da nota; reprodução da cadeia; amostrador corrigido) estão com o Dudu.
